# Security & Customer-Flow Audit — 2026-08-06

**Scope:** daisychain-site (Next.js 16 · Sanity · Stripe LIVE · Supabase · Shopify · beehiiv/Laylo/Resend)
**Method:** Codex-reviewed plan (`AUDIT-PLAN-2026-08-06.md`) → Phase 0 env gate → 6 parallel static reviewers, each self-adversarial → owner verification of headline claims against live production → Codex adversarial review of findings.
**Constraint:** zero production writes. Stripe preview is test-mode, but Supabase/Sanity/Shopify/beehiiv/Laylo/Resend are **shared with production**, so no dynamic purchase testing was performed. All findings are static + read-only proof.

**Verification legend:** ✅ = I confirmed against live production or ran the code path · 📄 = confirmed in source, not executed · ⚠️ = needs an owner check I could not perform read-only.

---

## Executive summary

Three issues let anyone take paid product for free or near-free, and all three are live right now:

1. **Master WAVs are published in public page source** — ✅ verified: a 28 MB `.wav` for a paid release downloads with no purchase, no login. The digital paywall is effectively off.
2. **Physical checkout charges a price supplied by the browser** — 📄 pay $0.01 for a $45 vinyl and a real Shopify draft order is still cut for fulfilment.
3. **The public Supabase key can read customer data, and (per schema) grant itself the $99 pass** — ✅ verified live: `download_tokens`, `guest_purchases`, `processed_stripe_events` all return rows to the anon key. Write capability is schema-confirmed but ⚠️ unverified live (verifying would require a production write).

Below these sit a broken guest-checkout price path, an entitlement bypass where any physical order unlocks the whole catalogue, and a missing security-header layer.

## CRITICAL

### C1 · Master WAV URLs ship in public release-page HTML ✅
`src/lib/queries.ts` (`RELEASE_DETAIL`, `audioUrl`) → `src/app/releases/[slug]/page.tsx` → `ReleaseInteractive.tsx` (client component)

`RELEASE_DETAIL` resolves `audioUrl` for non-upcoming tracks and the whole `tracks[]` array is passed into a **client** component, so the URLs serialize into the RSC payload in the HTML.

**Verified live:** `curl https://www.daisychainsd.com/releases/you-just-want-my-love` contains
`cdn.sanity.io/files/02wrtovm/production/93725246…wav`, and a HEAD on that URL returns `HTTP 200, audio/wav, content-length: 28544772, filename="YOU JUST WANT MY LOVE 16BIT.wav"`. No auth, no purchase, no JS.

**Impact:** every live release's masters are free to anyone who views source. This is the product.
**Fix:** set `"audioUrl": null` in `RELEASE_DETAIL` (the public page only needs `previewUrl`); same for `LATEST_RELEASE` and `HOMEPAGE_SETTINGS`. The gated queries (`RELEASE_DOWNLOAD`, `RELEASES_BY_SLUGS`, `ALL_RELEASES_DOWNLOAD_WITH_EARLY`) keep `audioUrl` behind entitlement checks.
**Structural note:** Sanity asset URLs are unguessable but permanent and unrevocable. Once leaked they work forever. Long-term fix is private assets + signed URLs or proxying downloads through an authenticated route.

### C2 · `/api/checkout-physical` charges a client-supplied price 📄
`src/app/api/checkout-physical/route.ts:27-44` — `unit_amount: Math.round(item.price * 100)`, `quantity: item.quantity`, both straight from the request body. **No auth on the route, no Shopify lookup, no variant validation.**

```
POST /api/checkout-physical
{"items":[{"variantId":"<real vinyl variant>","title":"…","price":0.5,"quantity":1}]}
```
Pay $0.50 + shipping. The webhook (`webhooks/stripe/route.ts:186-232`) replays `variantId`+`qty` from metadata into a **real Shopify draft order** with the buyer's address, ready to fulfil via Pirate Ship. Nothing in the fulfilment path surfaces the price mismatch.

Two extras on the same route: `quantity` is uncapped and never checked against stock (oversell on limited vinyl), and `title`/`imageUrl` are attacker-controlled and render on a `checkout.stripe.com` page under your Stripe account (phishing hosted on Stripe's domain, attributed to Daisy Chain).

**Fix:** resolve every `variantId` server-side via the Storefront API; take price/title/image from Shopify; accept only `variantId` + `quantity` from the client; validate `availableForSale`; cap quantity and `items.length`. `/api/checkout` already does this correctly with Sanity — copy the pattern.

### C3 · Public anon key reads customer data; schema grants it write ✅/⚠️
`supabase-schema.sql:39-41, 44-46, 49-51, 79, 92, 113-114`

Postgres policies with no `TO` clause default to `TO PUBLIC` — which includes `anon`. All five "Service role …" policies lack it, and the service role bypasses RLS anyway, so these policies exist only for anon/authenticated. There are also **no GRANT/REVOKE statements**, so Supabase's default grants to `anon` stand.

**✅ Verified live against production** with the browser-shipped anon key:

| Table | anon SELECT result |
|---|---|
| `download_tokens` | **returns rows** — live tokens + slug + buyer email |
| `guest_purchases` | **returns rows** — guest buyer emails, purchase history |
| `processed_stripe_events` | **returns rows** |
| `purchases` | 0 rows (correctly scoped to `auth.uid()`) |
| `profiles` | 0 rows (correctly scoped) |

The 2026-07-03 audit staged `scripts/fix-rls-guest-tables.sql` for exactly this. **It was never applied** — the leak is still open 34 days later. It also would not have been enough: it drops two policies and leaves the rest.

**⚠️ Unverified (would require a production write):** per schema, anon can also
- `UPDATE profiles … USING (true)` with no `WITH CHECK` → set `has_unlimited_pass = true` on any row → free $99 pass + 7-day pre-release access to unreleased masters
- `INSERT purchases … WITH CHECK (true)` → fabricate entitlements for any release
- `INSERT/DELETE download_tokens` → mint a token for any slug, or delete idempotency rows to re-arm webhook replay

**Owner verification (one query, Supabase SQL editor):**
```sql
select tablename, policyname, roles, cmd, qual, with_check
from pg_policies where schemaname='public';
```
**Fix — drop the permissive policies and revoke grants, then fold it into `supabase-schema.sql` so a re-run can't recreate it:**
```sql
drop policy if exists "Service role can update profiles"  on public.profiles;
drop policy if exists "Service role can insert profiles"  on public.profiles;
drop policy if exists "Service role can insert purchases" on public.purchases;
drop policy if exists "Service role full access"                            on public.download_tokens;
drop policy if exists "Service role full access on guest_purchases"         on public.guest_purchases;
drop policy if exists "Service role full access on processed_stripe_events" on public.processed_stripe_events;
revoke all on public.download_tokens, public.guest_purchases,
              public.processed_stripe_events from anon, authenticated;
```
Keep only the `auth.uid()`-scoped select/update-own policies. All server writes use the service-role client, which bypasses RLS — nothing legitimate breaks.

### C4 · Any paid session without `slug` metadata unlocks the entire catalogue 📄
`src/lib/verify-download.ts:49-50` — `if (purchasedSlug && purchasedSlug !== slug) return invalid`

The slug check is **skipped entirely when the session has no `slug` metadata**. Confirmed in source: physical sessions carry `{type:"physical", variants}` and cart sessions carry `{userId, type:"cart", cartTracks…}` — **neither has `slug`**.

The physical path hands the buyer the session id directly: `return_url: /shop/checkout/success?session_id={CHECKOUT_SESSION_ID}`. So: buy the cheapest merch item → copy `cs_live_…` from the address bar → `GET /download/<any-slug>?session_id=cs_live_…` for every release. `RELEASE_DOWNLOAD` (`queries.ts:70-88`) has **no `hidden`/`status` filter**, so this includes hidden and unreleased material. Stripe sessions are permanently retrievable, so the id never expires.

Chained with C2: **$6 buys a real vinyl and the whole catalogue including unreleased masters.**

**Codex addition:** **unlimited-pass sessions also lack `slug`** (`checkout-pass/route.ts:73`), so a pass session id is a third master key. `/api/verify-purchase` carries the identical bug (`verify-purchase/route.ts:27`).

**Fix:** require an affirmative match — `if (session.metadata?.slug !== slug) return invalid` — and **reject non-guest-digital session types by default**. Per Codex: do *not* simply "parse cart sessions" into bearer access — authenticated cart sessions must not become public download links; they should be rejected on `/download` unless a deliberate guest-cart flow exists with explicit metadata and expiry. Add `&& hidden != true && status != "upcoming"` to `RELEASE_DOWNLOAD`. Bound session access by `session.created` (e.g. 7 days).

## HIGH

### H1 · Guest checkout charges the wrong item at the wrong price 📄
`CartDrawer.tsx:58-69` → `LoginForm.tsx:93-105` → `api/checkout/route.ts:39-83`

The guest path drops everything except the **first item's slug** and no `trackKey`, so the API prices it as a **full-release** purchase. A guest with one $2 track in the cart sees "$2.00" and is charged the full release price; a guest with 3 tracks is charged for one release and the rest silently vanish. This affects every guest purchase that isn't a single full release.
**Fix:** carry the full cart through the guest path (the `cartItems` branch already prices server-side, it just lacks a guest identity path), or at minimum forward `trackKey` and block guest checkout for multi-item carts.

### H2 · Single-track buyers receive every track's WAV URL in the page payload 📄
`download/[slug]/page.tsx:73,86-87` → `DownloadPanel.tsx:45-48`

*Precision note from Codex:* `DownloadPanel` **does** filter by `purchasedTrackKey` before rendering links, so the UI is correct. The problem is one layer earlier — the server page passes the **full** `release.tracks` array (every `audioUrl`) into the client component, so all WAV URLs are serialized into the RSC payload regardless of what's rendered. Buy one $2 track off a 6-track EP, read the payload, take all six.
**Fix:** filter `release.tracks` **server-side** before passing the prop; keep the client filter as UI only. `/account` already does this correctly.

### H3 · Unreleased and hidden releases are buyable and downloadable 📄
`api/checkout/route.ts:67`, `queries.ts:71` — neither the checkout price lookup nor `RELEASE_DOWNLOAD` filters `status`/`hidden`. Upcoming slugs are public (the "Soon" pill). Buy an unreleased release at its listed price → download masters pre-embargo. Also makes `hidden` useless as a safety mechanism.
**Fix:** `&& hidden != true && status != "upcoming"` on both.

### H4 · Refunds and chargebacks don't revoke access 📄
`webhooks/stripe/route.ts:155-175` deletes `purchases`/`guest_purchases` rows but never touches `download_tokens`, and `verifyDownloadAccess` only checks `payment_status !== "paid"` — **a refund does not change a Checkout Session's `payment_status`**. So: buy → download → refund → keep downloading, permanently. The alert email reads as though access was removed.
**Fix:** delete download tokens on refund (add `revoked_at`), and expand `payment_intent.latest_charge` in `verifyDownloadAccess` to reject refunded sessions.

### H5 · Partial refunds delete all entitlements for the session 📄
`webhooks/stripe/route.ts:155` — `charge.refunded` fires on **any** refund including partial, and the handler never checks `amount_refunded` vs `amount`. Refund $2 of a $12 six-track cart → **all six** purchase rows deleted. Paying customer loses what they kept.
**Fix:** only revoke when `charge.refunded === true` (full) or on dispute; alert-only on partial.

### H6 · No durable record when fulfilment fails 📄
If `createDraftOrder` throws **and** the alert email fails (Resend unset → `email.ts:304` silently returns), a paid physical order leaves **no app-side record at all** — physical orders never write to Supabase, `processed_stripe_events` stores only the event id and actively prevents Stripe retry. Discovery requires manually diffing Stripe against Shopify. This has already happened twice (Sessions 5 and 6 both needed manual recovery scripts).
**Fix:** write a `fulfillments` row (`status: pending → done`) before attempting fulfilment; have the existing ops-health cron flag stale `pending` rows. This also gives C-adjacent M1 the status column it needs.

### H7 · Next.js 16.2.1 is behind ~23 advisories, several middleware-bypass ✅(probed) — *severity contested*

*Codex marks this OVERSTATED* on the grounds that the advisory list isn't verifiable from source alone. It isn't — it comes from `npm audit` output against the installed tree (`next` is a direct dependency; `fixAvailable: 16.3.0`, non-major), which I ran and recorded. I'm keeping it at High because the bypass class targets exactly the mechanism guarding `/ops`, but flagging the disagreement so you can weigh it.

`src/proxy.ts` middleware is the **only** gate on `/ops` (customer emails + revenue) and `/studio`. Multiple high-severity *Middleware/Proxy bypass* advisories affect 16.2.x.
**Probed live and the gate held** — RSC headers, prefetch segments, path normalisation, `x-middleware-subrequest` all returned 401. So: unpatched, not demonstrably exploited.
**Fix:** `npm i next@16.3.0` (non-major).

### H8 · `/api/convert` is unauthenticated compute with no size cap 📄
`api/convert/route.ts:72-76` — buffers the entire remote file into memory, no `Content-Length` check, no rate limit, 55s ffmpeg, `maxDuration=60`. The allowlist pins the **host** (`cdn.sanity.io`) but not the **project**, so any Sanity customer's public asset is a valid input. Each request = ~100 MB egress + seconds of CPU; unbounded concurrency starves the function pool, taking down checkout and downloads for real buyers.
Also: no `-f wav` / `-protocol_whitelist`, so ffmpeg's full demuxer set is exposed to attacker-chosen bytes (plausible LFI chain via HLS/concat demuxers; the ffmpeg-static build's current default whitelist is ⚠️ unverified).
**Fix:** pin the URL prefix to `https://cdn.sanity.io/files/02wrtovm/production/`, cap `content-length`, add `-f wav -protocol_whitelist file`, `redirect: "manual"`. Four lines.

## Security headers to add (`next.config.ts`)

Accounts for what the site actually loads: Sanity CDN, Adobe Typekit, Stripe embedded checkout, Google Docs iframe on `/ops/sops`, CMS `embedUrl` players, Shopify CDN, Supabase REST/realtime, and Studio's `eval`.

```ts
const csp = [
  "default-src 'self'",
  "script-src 'self' 'unsafe-inline' 'unsafe-eval' https://js.stripe.com",
  "style-src 'self' 'unsafe-inline' https://use.typekit.net https://p.typekit.net",
  "font-src 'self' data: https://use.typekit.net https://p.typekit.net",
  "img-src 'self' data: blob: https://cdn.sanity.io https://*.sanity.io https://cdn.shopify.com https://p.typekit.net",
  "media-src 'self' blob: https://cdn.sanity.io",
  "connect-src 'self' https://*.supabase.co wss://*.supabase.co https://*.sanity.io https://api.stripe.com https://*.myshopify.com https://use.typekit.net https://p.typekit.net",
  "frame-src 'self' https://js.stripe.com https://hooks.stripe.com https://docs.google.com https://bandcamp.com https://*.bandcamp.com https://w.soundcloud.com https://open.spotify.com",
  "worker-src 'self' blob:",
  "frame-ancestors 'self'", "base-uri 'self'", "form-action 'self'", "object-src 'none'",
  "upgrade-insecure-requests",
].join("; ");

async headers() {
  return [{ source: "/:path*", headers: [
    { key: "Content-Security-Policy", value: csp },
    { key: "Strict-Transport-Security", value: "max-age=63072000; includeSubDomains; preload" },
    { key: "X-Frame-Options", value: "SAMEORIGIN" },
    { key: "X-Content-Type-Options", value: "nosniff" },
    { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
    { key: "Permissions-Policy", value: "camera=(), microphone=(), geolocation=()" },
  ]}];
}
```
Ship as `Content-Security-Policy-Report-Only` for a day first — `/studio` and the Stripe iframe are most likely to trip it. To drop `'unsafe-eval'`, split into non-overlapping `/studio/:path*` and `/((?!studio).*)` entries.
